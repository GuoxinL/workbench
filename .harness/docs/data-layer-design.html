§0 概述

数据层是 workbench 的唯一可写数据入口。整体采用 local-first（本地优先）模型：所有写操作先落本地 IndexedDB（浏览器本地数据库，本机主存储），再由同步引擎在后台异步推送到 GitHub（可选接入的远端主存储，也是跨设备汇聚点 / convergence point）。视图层只通过 StorageLayer（存储层） 暴露的接口读写数据，永远不直接接触底层存储或 GitHub API。

本文档只描述既定目标架构，不含当前/历史实现细节。对应实现文件索引：src/stores/data.ts（store / 写盘）、src/services/sync/{engine,merge,serialize}.ts（同步）、src/services/github/{contents,manifest,repoFile,diagnose,client}.ts（远端）、src/types/index.ts（模型）。

红线约束（来自 AGENTS.md）

  • 红线 4 禁止绕过 src/stores/data.ts 直接读写 wb.* 键；禁止绕过 services/github/*、services/sync/* 直接调 GitHub API（否则脏标记/冲突合并/事件广播被绕开，引发数据丢失）。
  • 红线 5 GitHub Token 只可存于 wb.cfg.v1，禁止写入 data/workbench.json、日志或源码。
  • 安全基线 用户内容渲染前必须经 esc() 转义，禁止未转义拼接 innerHTML。

§1 目标架构（分层模型）

自上而下分为四层，依赖方向单向向下；视图层只面对 StorageLayer，底层是 IndexedDB（本机主存储）与 GitHub（可选远端主存储）双实现。写入采用 「View → IndexedDB（立即）→ GitHub（后台异步）」的 local-first 链路。

为什么 IndexedDB 是「极简默认」而非「临时缓存」：这个浏览器 IndexedDB 实现的命名是需求驱动的，不是技术降级——一个新用户第一次试用「个人工作台」时，不可能已经备好 GitHub 仓库 / Token / 分支。零配置、用浏览器原生存储即可完整启动，是产品冷启动的最小可行路径，也是默认模式。只有用户主动填好 GitHub 配置后，远端仓库才成为可选的主存储。因此在极简模式（minimal mode，零配置默认态）下，IndexedDB 就是唯一的主存储，而非"远端缓存的一份副本"；"临时"仅相对"可选接入的远端存储层"而言，不应理解为次等存储。
写入链路（View → IndexedDB → GitHub）：视图层只调用 StorageLayer.Save*/Delete*，① 写入立即落本地 IndexedDB（毫秒级、UI 不阻塞、离线可用），② 再由同步引擎在后台异步推送到 GitHub（图中虚线表示异步、非阻塞）。即"所有数据先写 IndexedDB，IndexedDB 再同步到 GitHub"——这是 local-first 本地优先模式：GitHub 是可选接入的远端主存储 / 跨设备汇聚点，离线时完全不依赖它。
"主存储"是双向汇聚，不是主从覆盖：本机 IndexedDB 是本机主存储（写入发生地、本机真相），GitHub 是远端主存储 / 跨设备汇聚点（多设备真相）。二者各为各自范围内的主存储，不是"GitHub 永远赢"的主从关系。同步语义是双向合并（按 updatedAt 的 LWW，见 §5.2），而非单向覆盖——若推时以本地为准、拉时以 GitHub 为准会两边互殴丢数据。多设备离线各改同一篇时，后同步者会静默覆盖先同步者，这是 LWW 的已知取舍，需在 UI/文档明示。

§2 数据模型与存储结构

2.1 实体 Schema（src/types/index.ts）

interface Todo {
  id; title; desc; color: ColorKey; status: 'todo'|'doing'|'done';
  due: string;            // 'YYYY-MM-DD'，空串无截止
  time: number;           // 用户可编辑创建时间
  articleId: string;      // 关联文章 id，空串无
  createdAt; updatedAt;
  deleted: boolean;       // 软删除墓碑（参与合并，可传播远端删除）
}
interface Article {
  id; title; content; fromTodo: string; tags: string[];
  createdAt; updatedAt;
  deleted: boolean;       // 墓碑（参与合并，可传播远端删除）
  published?: boolean;    // 是否发布到公开镜像库
}

Todo（待办事项）与 Article（文章）均经 StorageLayer 持久化：Todo 落 todos/<id>.json，Article 落 kb/<id>.md（见 §3 路由）。双向链接以正文 [[标题]] 形式存在，改标题时由 renameRefs 联动改写所有引用。

2.2 存储结构

（GitHub 仓库）		manifest.json{version:1, updatedAt, total, order:string[], articles:{[id]:{...}}, todos:{[id]:{...}}}轻量索引，含 total/order 供分页；per-file LWW 的 sha 缓存

图片存储按模式分两支（详见 §6）：极简（未填 GitHub）→ 本地 IndexedDB images；同步（已填 GitHub）→ git images/<hash>；外部对象存储图云为后续实现。

§3 存储层 / 数据层接口契约

存储层对上是统一接口，内部按实体类型路由到不同数据层实现；调用方（视图 / 业务）不感知底层是 GitHub 还是 IndexedDB。范围锁定如下：

决策点结论
存储层接口SaveTodo / SaveArticle / ListTodo / ListArticle / DeleteTodo / DeleteArticle；图片操作不作为独立接口，而是 Save* / Delete* 的内部副作用（见 §3.1 与 §6）
Todo 路由→ 本地 IndexedDB（本机主存储）+ 远端 GitHub（todos/<id>.json），与 Article 共用 StorageLayer 双写路径，按需同步
Article 路由→ 本地 IndexedDB + 远端 GitHub（kb/<id>.md），双向同步
分页覆盖含远端按页拉取：列表 / 读写按页；同步合并改为索引 / 分块驱动
浏览器实现IndexedDB（支持大量单实体文件 + 二进制图片 + 异步不阻塞）
图片存储按模式分两支：极简（未填 GitHub）→ 本地 IndexedDB；同步（已填 GitHub）→ git images/HASH；外部对象存储图云为后续实现（见 image-cloud-design.html）

3.1 存储层接口（StorageLayer）

interface StorageLayer {
  // ── Todo：本地 IndexedDB + 远端 GitHub 同步 ──
  SaveTodo(t: Todo): Promise<void>
  ListTodo(page: number, size: number): Promise<{ items: Todo[]; total: number }>
  DeleteTodo(id: string): Promise<void>        // 本地软删 / 物理删

  // ── Article：远端永久（GitHub 文件夹）──
  SaveArticle(a: Article): Promise<void>
  ListArticle(page: number, size: number): Promise<{ items: Article[]; total: number }>
  DeleteArticle(id: string): Promise<void>      // 墓碑，待同步传播

  // 注：图片上传/回收不再作为 StorageLayer 的独立方法。
  //     Save*/Delete* 内部根据"正文里引用了哪些图片"自动触发
  //     图云层的 put()/delete()（见 §6），调用方只面对实体接口。
}
图片是实体（Todo/Article）的内部细节而非独立资源：SaveTodo/SaveArticle/... 先写本地 IndexedDB、再异步同步到远端 GitHub（Todo → todos/<id>.json，Article → kb/<id>.md）；若正文含 !(...) 图片引用，存储层在写盘同时委托 ImageCloudLayer.put() 上传、在删除实体或正文去掉引用时委托 ImageCloudLayer.delete() 回收。视图层只面对 StorageLayer，不感知图云层。

3.2 DataLayer（数据层）接口与双实现

interface DataLayer {
  Save<T>(kind: 'todo'|'article', id: string, entity: T): Promise<void>
  Get<T>(kind: 'todo'|'article', id: string): Promise<T | null>
  List<T>(kind: 'todo'|'article', page: number, size: number): Promise<{ items: T[]; total: number }>
  Delete(kind: 'todo'|'article', id: string): Promise<void>
  // 索引：维护 total 与有序 id 列表，供分页与同步比对
  readIndex(): Promise<DataIndex>
}
实现承载物理结构
远端主存储（GitHub 文件夹）Todo + Article + 图片todos/<id>.json、kb/<id>.md（frontmatter+正文）、manifest.json（索引）、images/<hash>
本机主存储（浏览器 IndexedDB，需求驱动）Todo + Article：极简模式下为唯一主存储；同步模式下兼作本地快速启动层object store todos / articles，key = id；独立 index store 存分页元数据

§4 分页（pagination）与索引（index）· 减少全量遍历的核心

索引（index）是分页的前提：无论本地还是远端，都维护一份轻量 DataIndex（数据索引，不存正文）：

interface DataIndex {
  total: number
  order: string[]                       // 有序 id 列表（按 updatedAt 倒序）
  meta: Record<string, { updatedAt: number; deleted: boolean; sha?: string }>
}
  • 列表按页：ListTodo/ListArticle(page,size) 先读对应索引（GitHub 侧 manifest.json，本地侧 IndexedDB index store）→ 取 order.slice((page-1)*size, page*size) 的本页 id → 仅 GET 这些 todos/<id>.json / kb/<id>.md。全量遍历被降为 O(页大小)。
  • 本地 Todo 分页：IndexedDB 游标 cursor.advance((page-1)*size) + limit(size)，天然分页，无全量加载。
  • 同步合并改为索引驱动（含远端按页拉取）：拉取只取轻量 manifest.json → 与本地索引做 LWW（按 updatedAt，相等保留本地）→ 仅找出真有差异的实体 → 只 GET/PUT 这些变更文件。传输量从 O(N) 降到 O(差异数)。
关键转变：从"拉全部实体正文再合并"改为"拉索引 → 比对 → 只拉变更文件"。UI 分页与同步分块共用同一份索引，避免重复设计。

§5 同步机制

5.1 SyncPhase（同步状态机）

idle → syncing → ok | error | off
            ↑___________↓ (轮询 / 防抖推送循环)
  • off：未启用同步，或已启用但配置不完整（不发起请求，避免空 repo 触发误报）。
  • syncing：拉取/合并/推送进行中，驱动 UI 同步状态指示。

5.2 LWW（Last-Write-Wins，最后写入获胜）合并

以 id 为主键，updatedAt 大者胜，相等保留本地；合并后按 createdAt 倒序。墓碑（deleted:true）同样参与合并，保证删除可跨端传播。实现层会额外返回"是否发生变更"的标志，供上层判断是否需要推送。

function mergeEntities(local, remote){
  const map = new Map()
  for (const it of local) map.set(it.id, it)
  for (const r of remote){
    const l = map.get(r.id)
    if (!l || r.updatedAt > l.updatedAt) map.set(r.id, r)  // 远端较新则覆盖
  }
  return [...map.values()].sort((a,b)=> b.createdAt - a.createdAt)
}
取舍：LWW 是单用户多设备场景下的务实选择，但多设备离线各改同一篇时，后同步者会静默覆盖先同步者。若需更强保障，可演进为字段级合并 / CRDT（无冲突复制数据类型），但当前目标以 LWW 为基线并在 UI/文档明示该取舍。

5.3 墓碑（tombstone，软删除标记）TTL

软删除记录保留 TOMBSTONE_TTL = 30 天，过期后清理。保留窗口用于让删除操作有机会传播到其它端；窗口内保留的墓碑会被推送到远端。

5.4 乐观锁 & 冲突重试 & 并发

  • 乐观锁（optimistic locking）：推送 manifest.json / 单个 kb/<id>.md 时携带远端当前 sha；远端若已被改动，GitHub 返回 409。
  • 冲突重试（conflict retry）：发生冲突时，重拉远端合并后重试，最多 MAX_RETRY=3 次，退避 350 ms × attempt；超限置 phase='error'。每次重试必须重拉远端 manifest sha 作为乐观锁基准，不能用本地陈旧 sha，否则会陷入 409 死循环。
  • 并发排队（concurrency queue）：同步请求复用同一 in-flight Promise，避免"忙即返回"导致的写丢失。
  • 防抖（debounce）推送：PUSH_DEBOUNCE=1500 ms，连续编辑只触发一次同步。
  • 轮询（polling）：poll（默认 20000 ms，钳制 5 s~300 s），页面隐藏时跳过以省流量。
推送顺序约定：先逐文件 PUT 各实体（kb/<id>.md / todos/<id>.json），最后再 PUT manifest.json。这样读到 manifest 时视图始终一致，半推状态不会让读取方看到残缺数据。

§6 ImageCloudLayer（图云层）

图片存储按是否配置 GitHub分两支，外部对象存储（七牛/R2/OSS）为后续实现（设计见 image-cloud-design.html）。ImageCloudLayer 是存储层与具体图床之间的唯一隔离面——只暴露两个原语，不暴露到 StorageLayer 实体接口之上：

interface ImageCloudLayer {
  // 上传一张图，返回可引用 key（git 模式为 images/HASH，图云模式为完整 URL）
  put(blob: Blob): Promise<string>
  // 回收一张图（删除实体 / 正文去掉引用时调用）
  delete(key: string): Promise<void>
}
  • 极简模式（未填 GitHub 配置）：put(blob) 降级写入本地 IndexedDB images store（DataURL/blob），返回本地引用 key，文章引用本地 blob URL。
  • 同步模式（已填 GitHub 配置）：默认 git images/<hash>.<ext> → 返回 images/HASH 引用；文章正文以 ![](images/HASH) 引用。零额外依赖，可立即跑通。
  • 回收时机：存储层在 DeleteArticle/DeleteTodo 时，或 SaveArticle 发现正文引用的图片集合相对旧版本减少时，对"被丢弃的 key"调用 ImageCloudLayer.delete(key)，避免死图堆积（git 模式因墓碑传播，删除为软删，定期垃圾回收）。
  • 已知取舍（git 路径）：二进制进 git 会膨胀仓库、拖慢 Contents API 与克隆。仓库提供方宜加 .gitattributes 对 images/ 设 linguist-generated。
  • 图云（后续实现）：对象存储（Cloudflare R2 / S3 / OSS / 七牛）作为 git 路径的升级替代，仅替换 ImageCloudLayer 内部 put(blob)→url 与 delete(key) 的实现，文章正文改为存完整 URL（含服务端签名），其余层不变。详细接口设计见 image-cloud-design.html。

§7 生命周期与极简模式

本章先界定浏览器侧存储（IndexedDB）的生命周期，再定义极简模式：初始化时未填写任何 GitHub 相关配置，应用必须完整可运行。这是 local-first 模型的默认态，而非需要额外开发的特例。

7.1 浏览器侧存储生命周期（IndexedDB）

维度行为
作用域按 origin（协议+域名+端口）隔离；与 tab / 会话无关
留存跨会话、跨浏览器重启永久留存；无内置 TTL / 过期
消失途径① 应用主动 deleteDatabase / delete；② 用户手动清站点数据；③ 无痕模式会话结束清空；④ 存储压力回收（best-effort 型被 LRU 静默回收）；⑤ 分区存储清理连带

对本设计的含义：同步模式下 IndexedDB 是本地快速启动层，远端 GitHub 才是主存储（含 Todo 也落 todos/ID.json），因此本地被回收只是"下次从远端重拉"，不丢数据。而极简模式下 IndexedDB 本身就是唯一主存储（见 §1 需求驱动说明），此时本地被清即数据丢失，故 §7.5 建议在该模式主动申请 storage.persist() 降低回收概率。

7.2 极简模式定义

极简模式：启动时 Config 中 enabled=false 或 repo/branch/token 不完整（即 isConfigComplete(cfg)===false），应用仍须 100% 可用：

  • Todo / Article 的增删改查、双向链接、标题联动改写全部本地可用；
  • 图片：按 §6 的分支——极简模式（未填 GitHub）ImageCloudLayer.put(blob) 写入本地 IndexedDB images store（DataURL/blob），文章引用本地 blob URL；同步模式（已填 GitHub）走 git images/<hash>；外部对象存储图云为后续实现。删除/去引用时由存储层内部调用 ImageCloudLayer.delete(key) 回收。
  • 同步 / 冲突 / 轮询全部跳过，无任何网络请求，不报错、不卡启动。

7.3 需求存在性证明（为何极简模式天然成立）

极简模式不是新增特性，而是架构的默认降级态。证明链：

StorageLayer 双写路径：
  本地 IndexedDB 写入 = 同步 / 首要（必然成功，无网络依赖）
  远端 GitHub 同步    = 异步 / 可选

启动判定：
  isConfigComplete(cfg) === false  ──►  SyncEngine 置 phase='off'
                                     ──► save/list/delete 仅命中本地实现
  isConfigComplete(cfg) === true   ──►  启动轮询 + 立即 sync（同步模式）

结论：零配置 → 仅本地路径生效 → 应用完整可运行。
       故"极简可运行"是架构不变量，无需为它写专门分支。
flowchart TD
    START[应用启动] --> LOAD[加载本地 IndexedDB: todos / articles / index]
    LOAD --> CFG{配置完整? isConfigComplete}
    CFG -->|否 极简模式| OFF[phase = off 仅本地 IndexedDB]
    CFG -->|是 同步模式| ON[启动轮询 加 立即 sync]

7.5 生命周期兜底（实现 P0 必做）

  • 持久化申请：StorageLayer 初始化时 await navigator.storage.persist()，降低本地被静默回收导致频繁全量重拉。
  • 配额保护：写前 estimate() 评估；捕获 QuotaExceededError 提示用户清理或减小图片。
  • 回收自愈：IndexedDB 被清后，极简模式以空库启动仍可用；同步模式下则从远端重新拉取恢复，无需特殊处理。

7.6 验证（存在性证明的可执行化）

建议补集成测试固化该不变量：不写任何 GitHub 配置启动 → 断言 addTodo / updateArticle / 双向链接 全部成功，且 GitHub API 从未被调用。该测试即"极简模式需求存在性"的机器证明。

归并到 §8 落地计划：7.5 的 persist()/estimate()/QuotaExceededError 处理应并入 P0（IndexedDB 承载时一并落地）；7.6 测试作为 P0 的验收门槛。

§8 落地步骤与风险

8.1 落地步骤与优先级

批次项说明
P0① 抽象 DataLayer 接口 + IndexedDB 实现（承载 Todo）先把 Todo 从单 blob 迁到单实体 + 索引分页，验证分页降遍历收益
P0② 引入 DataIndex，ListTodo/ListArticle 按页本地游标分页；远端先读 manifest 索引
P1③ StorageLayer 路由：统一双写（本地 IndexedDB + 远端 GitHub 同步），Todo 与 Article 共用视图层切到 StorageLayer，隐藏底层差异
P1④ 远端单文件化 kb/<id>.md + todos/<id>.json + manifest 仅存索引替换原有全量推送/拉取
P2⑤ 同步合并索引驱动（只拉变更文件）把"全量拉正文合并"改为"索引比对 + 差分拉取"
P2⑥ 图片存储落地（极简 IndexedDB / 同步 git），预留对象存储图云切换点接口留扩展，图云为后续实现

8.2 风险与回退

  • 迁移兼容：旧单 blob 需在首次启动迁移为 IndexedDB 单实体 + 索引；远端 manifest 字段扩展为含 total/order，读取端对未知字段向后兼容。
  • 路由一致性：Todo 与 Article 共用"本地 + 远端"双写路径，路由层需保证两者索引（total/order）同步更新，可用单测覆盖。
  • 索引与实体不一致：写实体必须同步更新索引（同事务 / 同批次），否则分页 total 失真；IndexedDB 可用事务保证原子，GitHub 侧以 manifest 为索引权威。
  • 回退：分阶段合入，每批保持视图层 API 不变；若 IndexedDB 实现受阻，P0 可先保留单 blob 但加索引分页作为过渡。
