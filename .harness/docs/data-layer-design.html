§0 概述

数据层是 workbench 的唯一持久化真相源，负责：本地内存态管理、localStorage 落盘、远端 GitHub 仓库的拉取/推送与冲突合并。视图层（Vue 组件）只通过 Pinia store 暴露的 computed 与方法读写数据， 永远不直接接触 localStorage 或 GitHub API。

红线约束（来自 AGENTS.md）

  • 红线 4 禁止绕过 src/stores/data.ts 直接读写 wb.* 键；禁止绕过 services/github/*、services/sync/* 直接调 GitHub API（否则脏标记/冲突合并/事件广播被绕开，引发数据丢失）。
  • 红线 5 GitHub Token 只可存于 wb.cfg.v1，禁止写入 data/workbench.json、日志或源码。
  • 安全基线 用户内容渲染前必须经 esc() 转义，禁止未转义拼接 innerHTML。

核心文件索引：src/stores/data.ts（store）、src/services/sync/{engine,merge,serialize}.ts（同步）、src/services/github/{contents,manifest,repoFile,diagnose,client}.ts（远端）、src/types/index.ts（模型）。

§2 存储结构

2.1 本地（localStorage，4 个键）

键类型 / 内容是否同步远端说明
wb.data.v1WorkbenchData{version:1, todos:Todo[], articles:Article[], updatedAt}仅 articles 上传主数据；每次 touch() 全量序列化写入
wb.cfg.v1Config{enabled,repo,branch,path,token,poll,apiBase,publicRepo?}否含 token；永不落远端（红线 5）
wb.manifestSha.v1string（manifest.json 的乐观锁 sha）回填空推远端成功后回填，避免 409 冲突
wb.seeded"1"否首次播种示例数据标记，仅一次

2.2 远端（GitHub 仓库 workbench-data）

路径结构作用
manifest.json{version:1, updatedAt, articles:{[id]:{id,title,updatedAt,deleted,sha}}, todosSha}轻量索引，避免每次拉全量；per-file LWW 的 sha 缓存
kb/<id>.mdfrontmatter（id/title/createdAt/updatedAt/deleted/fromTodo/tags/publish）+ Markdown 正文每篇文章一个文件，便于版本追溯与冲突隔离

2.3 实体 Schema（src/types/index.ts）

interface Todo {
  id; title; desc; color: ColorKey; status: 'todo'|'doing'|'done';
  due: string;            // 'YYYY-MM-DD'，空串无截止
  time: number;           // 用户可编辑创建时间
  articleId: string;      // 关联文章 id，空串无
  createdAt; updatedAt;
  deleted: boolean;       // 软删除墓碑（仅本地，不上传）
}
interface Article {
  id; title; content; fromTodo: string; tags: string[];
  createdAt; updatedAt;
  deleted: boolean;       // 墓碑（参与合并，可传播远端删除）
  published?: boolean;    // 是否发布到公开镜像库
}

Todo 当前仅存本地、不进同步（§6 重构后将支持远端同步，落为 todos/<id>.json）；Article 经由 kb/<id>.md 双向同步。双向链接以正文 [[标题]] 形式存在，改标题时由 renameRefs 联动改写所有引用（L11）。

§3 数据访问时机

3.1 时序总览

时机触发点行为
冷启动useDataStore() 定义执行loadData/Config/ManifestSha 读盘 → engine.sync() + engine.startPolling()
读（响应式）组件 computedtodos/articles；articleById/todoById 按需 find（过滤墓碑）
写（业务）add*/update*/remove*改内存 → touch() → persist()（写 wb.data.v1）+ engine.schedulePush()（防抖 1.5s 推远端）
批量batch(fn)批内仅一次 persist + 脏标记
跨标签页window 'storage'mergeLWW 合并 articles/todos，不回写避免 ping-pong
配置变更saveConfig()停/启轮询 + 立即 sync(true)
手动同步SyncChip 点击store.sync(true)
发布镜像setPublished()并行 publishToMirror / unpublishFromMirror

3.2 一次写入的完整链路

组件调用 store.updateArticle(id, patch)
  └─ 内存 data.value.articles[i] = {...next, updatedAt: Date.now()}
  └─ touch()
       ├─ dirty = true
       ├─ persist()  → JSON.stringify(cleanupTombstones(data)) → wb.data.v1
       └─ engine.schedulePush()  → setTimeout(1500) → engine.sync(false)
                                         ├─ fetchRemote() 拉 manifest + kb/*.md
                                         ├─ mergeArticles(local, remote)  LWW
                                         ├─ applyRemote() 写回内存 + persist()
                                         └─ pushRemote()  逐文件 PUT kb/.md + manifest.json
                                                              （冲突则重试 ≤3 次）
关键点：Todo 的增删改不触发 schedulePush（只 touch 落本地）；只有 Article 变更才会推远端。落盘为全量序列化，是大数据量下的性能瓶颈（见 §5）。

§4 同步机制

4.1 同步状态机（SyncPhase）

idle → syncing → ok | error | off
            ↑___________↓ (轮询 / 防抖推送循环)
  • off：未启用同步，或已启用但配置不完整（不发起请求，避免空 repo 触发 404 误报）。
  • syncing：拉取/合并/推送进行中，由 adapter.setPhase 驱动 UI（SyncChip）。

4.2 LWW 合并（services/sync/merge.ts）

以 id 为主键，updatedAt 大者胜，相等保留本地；合并后按 createdAt 倒序。墓碑（deleted:true）同样参与合并，保证删除可跨端传播。

function mergeEntities(local, remote){
  const map = new Map()
  for (const it of local) map.set(it.id, it)
  for (const r of remote){
    const l = map.get(r.id)
    if (!l || r.updatedAt > l.updatedAt) map.set(r.id, r)  // 远端较新则覆盖
  }
  return [...map.values()].sort((a,b)=> b.createdAt - a.createdAt)
}

4.3 墓碑 TTL（services/sync/serialize.ts）

软删除记录保留 TOMBSTONE_TTL = 30 天，过期后在 cleanupTombstones（序列化前）清理。保留窗口用于让删除操作有机会传播到其它端；窗口内保留的墓碑会被推送到远端。

4.4 乐观锁 & 冲突重试（engine.ts / contents.ts）

  • 乐观锁：推送 manifest.json / 单个 kb/<id>.md 时携带远端当前 sha；远端若已被改动，GitHub 返回 409。
  • 冲突重试：conflictSlug !== null 时，重拉远端合并后重试，最多 MAX_RETRY=3 次，退避 350ms × attempt；超限置 phase='error'。
  • 并发排队：inFlight Promise 复用，避免"忙即返回 false"导致的写丢失（commit 81429d7）。
  • 防抖推送：PUSH_DEBOUNCE=1500ms，连续编辑只触发一次同步。
  • 轮询：poll（默认 20000ms，钳制 5s~300s），document.hidden 时跳过以省流量。
已踩坑固化：冲突重试循环每次必须重拉远端 manifest sha 作为乐观锁基准，不能用本地陈旧 sha，否则 409 → 死循环（见 engine.ts:88 注释）。

§5 优化建议落地设计

以下 7 项基于现状评估，按收益/风险排序。每项含动机、代码草图与影响面。均为非破坏性重构，保持 store 对外 API 不变，视图层无需改动。

高收益·低风险 ① Store 启动副作用解耦

动机：engine.sync() 与 startPolling() 写死在 useDataStore() 定义体内（data.ts:303-304），首次任意组件使用 store 即触发网络与定时器，难以测试与控制生命周期（如 HMR、测试环境）。

// 现状
const engine = createSyncEngine(adapter, { fetchRemote, pushRemote })
engine.sync(); engine.startPolling()   // 副作用耦合在定义体

// 改为显式 init()
let started = false
function init(){ if (started) return; started = true; engine.sync(); engine.startPolling() }
return { ..., init }

// App.vue
const store = useDataStore()
onMounted(() => store.init())

影响面：仅 data.ts + App.vue；store 返回集增加 init。

高收益·中风险 ② 落盘节流 + 分片存储

动机：persist() 每次 JSON.stringify(cleanupTombstones(data)) 全量写入，文章/待办量大时主线程阻塞、写放大严重（每次编辑都重写整个数据集）。

// 节流：合并多次 touch 到空闲帧
let pending = false
function schedulePersist(){
  if (pending) return
  pending = true
  const run = () => { pending = false; persist() }
  (window.requestIdleCallback || ((f)=>setTimeout(f,200)))(run)
}

// 分片（可选，配合 per-file LWW 天然契合）：
//   wb.article.<id> = 单篇序列化；wb.todo.<id> = 单条
//   索引 wb.data.v1 仅存 id 列表 + 元信息
//   加载时按需拼装；写入只落变更的那一篇

影响面：data.ts 的 loadData/persist/touch；若分片需改 applyRemote 与 storage 合并逻辑。

低effort·中收益 ③ Config 缓存

动机：adapter.getConfig() 在 sync 每轮、startPolling 每次都 JSON.parse(localStorage)（data.ts:279,281）。配置变更极少，重复解析浪费。

let cfgCache: Config | null = null
function loadConfig(): Config {            // 首次读盘并缓存
  if (cfgCache) return cfgCache
  ...原逻辑...
  cfgCache = raw ? parsed : fallback
  return cfgCache
}
function saveConfig(cfg){ cfgCache = cfg; localStorage.setItem(CFG_KEY, JSON.stringify(cfg)); ... }

影响面：仅 data.ts 内的 loadConfig/saveConfig。

低effort ④ 清理死字段 todosSha

动机：Manifest.todosSha 在类型与 emptyManifest() 中存在，但当前 Todo 未同步、该字段未被写入，属无效字段，误导后续维护者；若 §6 落地 Todo 远端同步，此字段可重新启用为 Todo 的 sha 索引，否则应清理。

// src/types/index.ts
interface Manifest { version:1; updatedAt:number; articles:Record<string,ManifestEntry> }
// 删除 todosSha 字段及其在 manifest.ts 中的赋值

影响面：types/index.ts、github/manifest.ts；需同步检查远端已存在的 manifest.json 兼容性（读取时忽略未知字段即可）。

中收益·中风险 ⑤ 跨标签同步 manifestSha

动机：storage 事件只合并 articles/todos，不合并 manifestSha。多标签页各自持不同乐观锁 → 冲突重试概率上升。

window.addEventListener('storage', (e) => {
  if (e.key === MANIFEST_SHA_KEY && e.newValue) {
    manifestSha.value = e.newValue
    return
  }
  if (e.key !== DATA_KEY || !e.newValue) return
  ...原 mergeLWW 逻辑...
})

影响面：data.ts 的 storage 监听；需确认 manifest.json 写入后 sha 已落 wb.manifestSha.v1（当前 setManifestSha 已写盘）。

低风险提醒 ⑥ 写失败不再静默吞掉

动机：persist() / setItem 异常被 catch 静默吞掉（data.ts:114,296）。配额满或隐私模式会静默丢数据，用户无感知。

function persist(){
  data.value.updatedAt = Date.now()
  try { localStorage.setItem(DATA_KEY, JSON.stringify(cleanupTombstones(data.value))) }
  catch (e) { adapter.setPhase('error'); console.warn('[data] 本地落盘失败', e) }
}

影响面：data.ts；建议配合 UI 暴露（SyncChip 已有 error 态可复用）。

低概率 ⑦ uid 防碰撞

动机：uid() 用 Date.now()+random，极端高频并发（同毫秒）有极小碰撞风险。

function uid(): string {
  return (crypto.randomUUID?.() ?? (Date.now().toString(36)+Math.random().toString(36).slice(2,10)))
}

影响面：仅 data.ts 的 uid()，无外部契约变化。

落地优先级建议

批次项理由
P0（必做）① 启动解耦、② 落盘节流稳定性收益最大、改动集中、风险可控
P1（建议）③ config 缓存、⑤ 跨标签 manifestSha、⑥ 写失败提示修复具体缺陷，改动小
P2（可选）④ 死字段清理、⑦ uid 强化整洁度/健壮性，可随缘
②的分片存储为可选增强；若先只做"节流"已能缓解主线程阻塞，分片可后续独立评估。所有改动均保持 store 对外方法签名不变，视图层零改动。分片存储的完整重构方案见 §6（单实体文件化 + 分页 + 索引驱动同步）。

§6 存储层 / 数据层重构方案（单实体文件化 + 分页 + 索引驱动同步）

本节基于已达成共识的分层模型，给出可落地的重构方案。目标：① 把"全量单 blob"改为单实体一个文件，减少写入放大；② 引入分页（page / size / total）与索引，降低全量遍历次数；③ Todo 与 Article 均经 StorageLayer 统一持久化，本地 IndexedDB 缓存 + 远端 GitHub 永久存储（按需同步）。

决策点结论
存储层接口SaveTodo / SaveArticle / ListTodo / ListArticle / DeleteTodo / DeleteArticle + SaveImage
Todo 路由→ 本地 IndexedDB 缓存 + 远端 GitHub 永久存储（todos/<id>.json），与 Article 共用 StorageLayer 双写路径，按需同步
Article 路由→ 本地 IndexedDB 缓存 + 远端 GitHub 永久存储（kb/<id>.md），双向同步

6.3 存储层接口契约（StorageLayer）

存储层对上是统一接口，内部按实体类型路由到不同数据层实现；调用方（视图 / 业务）不感知底层是 GitHub 还是 IndexedDB。

interface StorageLayer {
  // ── Todo：本地 IndexedDB 缓存 + 远端 GitHub 同步 ──
  SaveTodo(t: Todo): Promise<void>
  ListTodo(page: number, size: number): Promise<{ items: Todo[]; total: number }>
  DeleteTodo(id: string): Promise<void>        // 本地软删 / 物理删

  // ── Article：远端永久（GitHub 文件夹）──
  SaveArticle(a: Article): Promise<void>
  ListArticle(page: number, size: number): Promise<{ items: Article[]; total: number }>
  DeleteArticle(id: string): Promise<void>      // 墓碑，待同步传播

  // ── 图云 ──
  SaveImage(blob: Blob): Promise<string>        // 返回可引用 url
}
路由规则写在存储层内部：SaveTodo/SaveArticle/... 均先写本地 IndexedDB 缓存、再异步同步到远端 GitHub（Todo → todos/<id>.json，Article → kb/<id>.md）；视图层只面对 StorageLayer。

6.4 数据层实现（DataLayer 接口 + 双实现）

interface DataLayer {
  Save<T>(kind: 'todo'|'article', id: string, entity: T): Promise<void>
  Get<T>(kind: 'todo'|'article', id: string): Promise<T | null>
  List<T>(kind: 'todo'|'article', page: number, size: number): Promise<{ items: T[]; total: number }>
  Delete(kind: 'todo'|'article', id: string): Promise<void>
  // 索引：维护 total 与有序 id 列表，供分页与同步比对
  readIndex(): Promise<DataIndex>
}
实现承载物理结构
永久实现（GitHub 文件夹）Todo + Article + 图片todos/<id>.json、kb/<id>.md（frontmatter+正文）、manifest.json（索引）、images/<hash>
临时实现（浏览器 IndexedDB）Todo + Article 本地缓存object store todos / articles，key = id；独立 index store 存分页元数据

6.5 分页与索引（减少全量遍历的核心）

索引是分页的前提：无论本地还是远端，都维护一份轻量 DataIndex（不存正文），形如：

interface DataIndex {
  total: number
  order: string[]                       // 有序 id 列表（按 updatedAt 倒序）
  meta: Record<string, { updatedAt: number; deleted: boolean; sha?: string }>
}
  • 列表按页：ListTodo/ListArticle(page,size) 先读对应索引（GitHub 侧 manifest.json，本地侧 IndexedDB index store）→ 取 order.slice((page-1)*size, page*size) 的本页 id → 仅 GET 这些 todos/<id>.json / kb/<id>.md。全量遍历被降为 O(页大小)。
  • 本地 Todo 分页：IndexedDB 游标 cursor.advance((page-1)*size) + limit(size)，天然分页，无全量加载。
  • 同步合并改为索引驱动（含远端按页拉取）：拉取只取轻量 manifest.json → 与本地索引做 LWW（按 updatedAt，相等保留本地）→ 仅找出真有差异的实体 → 只 GET/PUT 这些变更文件。不再为合并而全量拉取正文，传输量从 O(N) 降到 O(差异数)。
关键转变：原 fetchRemote 是"拉全部 kb/*.md 再合并"，重构后是"拉索引 → 比对 → 只拉变更文件"。UI 分页与同步分块共用同一份索引，避免重复设计。

6.6 图云层（ImageCloudLayer）

  • 默认 git（quick start）：SaveImage(blob) 计算内容哈希 → 落 images/<hash>.<ext> → 返回 images/HASH 引用；文章正文以 ![](images/HASH) 引用。零额外依赖，可立即跑通。
  • 已知取舍：二进制进 git 会膨胀仓库、拖慢 Contents API 与克隆。仓库提供方宜加 .gitattributes 对 images/ 设 linguist-generated 或后续迁对象存储。
  • 可换对象存储：图云层内部抽象 put(blob)→url，未来实现切换为 Cloudflare R2 / S3 / OSS 时，仅替换该层，文章只存 URL 不变。

6.7 落地步骤与优先级

批次项说明
P0① 抽象 DataLayer 接口 + IndexedDB 实现（承载 Todo）先把 Todo 从 wb.data.v1 全 blob 迁到单实体 + 索引分页，验证分页降遍历收益
P0② 引入 DataIndex，ListTodo/ListArticle 按页本地游标分页；远端先读 manifest 索引
P1③ StorageLayer 路由：统一双写（本地 IndexedDB 缓存 + 远端 GitHub 同步），Todo 与 Article 共用视图层切到 StorageLayer，隐藏底层差异
P1④ 远端单文件化 kb/<id>.md + manifest 仅存索引替换现有全量 pushRemote/fetchRemote
P2⑤ 同步合并索引驱动（只拉变更文件）把"全量拉正文合并"改为"索引比对 + 差分拉取"，完成含远端按页拉取目标
P2⑥ 图云默认 git 落地，预留对象存储切换点先 quick start，接口留扩展

6.8 风险与回退

  • 迁移兼容：旧 wb.data.v1 单 blob 需在首次启动迁移为 IndexedDB 单实体 + 索引；远端旧 manifest.json 字段扩展为含 total/order，读取端对未知字段向后兼容。
  • 路由一致性：Todo 与 Article 共用"本地缓存 + 远端同步"双写路径，路由层需保证两者索引（total/order）同步更新，可用单测覆盖。
  • 索引与实体不一致：写实体必须同步更新索引（同事务 / 同批次），否则分页 total 失真；IndexedDB 可用事务保证原子，GitHub 侧以 manifest 为索引权威。
  • 回退：分阶段合入，每批保持视图层 API 不变；若 IndexedDB 实现受阻，P0 可先保留 wb.data.v1 但加索引分页作为过渡。

§7 生命周期与极简模式（需求存在性证明）

本章先界定浏览器侧存储（IndexedDB）的生命周期，再定义极简模式：初始化时未填写任何 GitHub 相关配置，应用必须完整可运行。并论证该需求在当前架构下天然成立（存在性证明），而非需要额外开发的特例。

7.1 浏览器侧存储生命周期（IndexedDB）

维度行为
作用域按 origin（协议+域名+端口）隔离；与 tab / 会话无关
留存跨会话、跨浏览器重启永久留存；无内置 TTL / 过期
消失途径① 应用主动 deleteDatabase / delete；② 用户手动清站点数据；③ 无痕模式会话结束清空；④ 存储压力回收（best-effort 型被 LRU 静默回收）；⑤ 分区存储清理连带
配额每 origin 动态配额（量级 GB）；写满抛 QuotaExceededError；navigator.storage.estimate() 查 usage/quota
持久化开关navigator.storage.persist() 申请持久化（获批后免于存储压力回收，仅用户手动清才丢）；默认 best-effort 可被回收
事务持久性默认 durability:'default'（崩溃安全）；'strict' 强制 fsync（更慢）
对本设计的含义：IndexedDB 是本地缓存层，远端 GitHub 才是永久真相源（含 Todo 也落 todos/ID.json）。因此本地被回收只是"下次从远端重拉"，不丢数据——这是把本地层设为可驱逐的安全前提。

7.2 极简模式定义

极简模式：启动时 Config 中 enabled=false 或 repo/branch/token 不完整（即 isConfigComplete(cfg)===false），应用仍须 100% 可用：

  • Todo / Article 的增删改查、双向链接、标题联动改写全部本地可用；
  • 图片：图云默认 git 需远端仓库，故极简模式下 SaveImage 降级为本地——写入 IndexedDB images store（DataURL/blob），文章引用本地 blob URL；配置远端后可迁移到 git；
  • 同步 / 冲突 / 轮询全部跳过，无任何网络请求，不报错、不卡启动。

7.3 需求存在性证明（为何极简模式天然成立）

极简模式不是新增特性，而是架构的默认降级态。证明链：

StorageLayer 双写路径：
  本地 IndexedDB 写入 = 同步 / 首要（必然成功，无网络依赖）
  远端 GitHub 同步    = 异步 / 可选

启动判定：
  isConfigComplete(cfg) === false  ──►  SyncEngine 置 phase='off'
                                     （与现有 engine.ts:67-75 的 off 分支一致）
                                     ──► save/list/delete 仅命中本地实现
  isConfigComplete(cfg) === true   ──►  启动轮询 + 立即 sync（同步模式）

结论：零配置 → 仅本地路径生效 → 应用完整可运行。
       故"极简可运行"是架构不变量，无需为它写专门分支。
flowchart TD

7.5 生命周期兜底（实现 P0 必做）

  • 持久化申请：StorageLayer 初始化时 await navigator.storage.persist()，降低本地缓存被静默回收导致频繁全量重拉。
  • 配额保护：写前 estimate() 评估；捕获 QuotaExceededError 提示用户清理或减小图片。
  • 回收自愈：IndexedDB 被清后，极简模式以空库启动仍可用；同步模式下则从远端重新拉取恢复，无需特殊处理。

7.6 验证（存在性证明的可执行化）

建议补集成测试固化该不变量：不写任何 GitHub 配置启动 → 断言 addTodo / updateArticle / 双向链接 全部成功，且 fetch（GitHub API）从未被调用（mock 计数 0）。该测试即"极简模式需求存在性"的机器证明。

归并到 §6 落地计划：7.5 的 persist()/estimate()/QuotaExceededError 处理应并入 P0（IndexedDB 承载 Todo 时一并落地）；7.6 测试作为 P0 的验收门槛。
