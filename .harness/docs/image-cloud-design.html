图云（Image Cloud）接入设计方案

维护者：Guoxin.Liu <lgx31@sina.cn> ｜ 最后更新：2026-08-02 ｜ 状态：设计稿（待确认后进入 SOP 实现）
目标：把文章内联的 base64 图片改为外置到可插拔的图床/对象存储，正文只存可访问 URL。 本方案只定义 接口与插件契约，让接入方按接口即可迅速实现任意图云「插件」，且对现有同步层零侵入。

1. 设计原则

  • 可插拔（Plugin）：每种图云是一个独立适配器（adapter），通过统一接口注册进框架；新增图云 = 新增一个适配器文件，不动核心代码。
  • AI 开发友好：接口签名固定、单一职责；每个适配器自带 configSchema 声明所需配置字段，AI/开发者读一个参考实现即可照葫芦画瓢产出新插件。
  • 配置化：图云选择在「设置 · 同步」页可配置——下拉选 provider + 按 configSchema 动态渲染字段 + 「测试连接」。配置只存本地 wb.cfg.v1。
  • 密钥不下发（红线 5）：图云的 SecretKey / 私钥永远不进前端、不进 data/workbench.json、不打日志。签名在服务端（Worker / 云函数）完成，前端只拿一次性上传凭证。
  • 与同步解耦：图片以 URL 存进 article.content 后，kb/<id>.md 体积骤降，现有 manifest + 逐文件同步逻辑完全不用改（详见 §9）。本方案只替换「图片从哪来」。

2. 整体架构与数据流

┌──────────── 浏览器（工作台前端） ────────────┐
│                                               │
│  Markdown 编辑器 ──粘贴/选择图片──▶ compress() │  (现有 src/lib/image.ts，仅压不内联)
│                                               │
│  useImageUpload (框架统一编排，非插件职责)      │
│     │ 1. adapter.issueUploadCredential()      │
│     │      └─► 若 signerKind='remote'         │
│     │            POST {signerUrl} ─────────────┼──▶ 签名服务(Worker/云函数，持 Secret)
│     │                ◀── 一次性 UploadCredential┼──  返回直传 URL + 头/表单
│     │ 2. 直传 Blob 到图云 (PUT/POST，按 cred)  │
│     │ 3. adapter.urlFor(key) ─▶ 图片 URL       │
│     ▼                                          │
│  把 ![](url) 写入 article.content              │
└───────────────────────────────────────────────┘
        │                                          │
        ▼  (不改)                                  │ (外部)
  现有同步引擎 ──▶ GitHub 仓库 kb/<id>.md       │ 图云对象存储（七牛/COS/OSS/R2…）
  (正文已是小巧的 URL 文本)                         │
要点：上传编排（useImageUpload）是框架提供的，所有适配器复用它；适配器只回答三个协议问题——「怎么拿凭证」「凭证怎么用」「key 怎么变 URL」。

3. 核心接口设计（TypeScript）

落点建议：src/services/imagehost/types.ts（接口）+ src/services/imagehost/registry.ts（注册表）+ src/services/imagehost/adapters/*.ts（各插件）+ src/services/imagehost/useImageUpload.ts（编排）。

3.1 配置与字段声明

/** 图云配置，整体挂在 Config.imageHost（仅存本地 wb.cfg.v1，永不上传） */
export interface ImageHostConfig {
  provider: string            // 适配器 id，如 'qiniu' | 'cos' | 'oss' | 'r2' | 'upgit'
  enabled: boolean
  /** 远端签名服务地址（signerKind='remote' 时必填）。持 Secret 的服务端，URL 本身非机密 */
  signerUrl?: string
  /** 其余字段由 adapter.configSchema 声明，例如：
   *  bucket / region / endpoint / cdnHost / baseUrl / publicRead / maxAgeSec … */
  [key: string]: unknown
}

/** 设置页动态渲染字段的声明——字段命名对齐 PicGo Uploader 契约（见 §14），便于复用社区上传器逻辑 */
export interface ConfigField {
  name: string                                   // 原 key：字段名，作配置对象的 key
  alias?: string                                 // 原 label：GUI 表单标题
  type: 'input' | 'password' | 'url' | 'number' | 'list' | 'confirm'
  required?: boolean
  default?: unknown                              // 默认值（对齐 PicGo）
  message?: string                               // 原 placeholder：占位/提示
  choices?: { name: string; value: string }[]    // 原 options：对齐 PicGo choices（type='list' 用）
  tips?: string                                  // 原 help：tooltip（对齐 PicGo tips）
  secret?: boolean                               // 本方案扩展：标记敏感字段，remote 模式下不落前端（由服务端持有）
}

3.2 上传凭证（前端直传用）

/** 适配器签发/返回的一次性上传凭证，前端据此直传，无需 Secret */
export interface UploadCredential {
  method: 'PUT' | 'POST' | 'POST-FORM'
  url: string                                   // 直传目标（含/不含 query 签名）
  headers?: Record<string, string>             // PUT / POST 头部（如 Authorization / x-*）
  formFields?: Record<string, string>          // POST-FORM 的 <input type=hidden>
  fileKey: string                              // 成功后用于 urlFor 的对象 key
  expiresAt?: number                           // 凭证过期时间戳（ms），编排层据此提前刷新
}

export interface UploadMeta {
  fileName: string                             // 原始文件名（用于扩展名）
  mime: string                                // image/webp 等
  size: number
  width?: number
  height?: number
  /** 建议的对象 key 前缀，如 'wb/<articleId>/'，适配器可忽略改用自有规则 */
  suggestedPrefix?: string
}

3.3 适配器接口（插件契约）

export interface ImageHostAdapter {
  /** 唯一 id，对应 Config.provider */
  readonly id: string
  /** 展示名（设置页下拉用） */
  readonly name: string
  /** 驱动设置页动态渲染的配置字段 */
  readonly configSchema: ConfigField[]

  /**
   * 密钥持有方式：
   *  - 'remote'：Secret 在服务端 signerUrl 处，前端只拿一次性凭证（推荐，守红线 5）
   *  - 'local' ：Secret 也在前端 cfg 中（仅开发/自签场景，标记不安全）
   *  - 'none'  ：无需密钥（如公开可写桶，极不推荐，仅匿名演示）
   */
  readonly signerKind: 'remote' | 'local' | 'none'

  /** 配置是否完整（对应现有 isConfigComplete 思路，决定是否可用） */
  isConfigComplete(cfg: ImageHostConfig): boolean

  /**
   * 申请上传凭证。框架在每次上传前调用。
   * - signerKind='remote'：内部 POST signerUrl（携带 meta + 非机密 cfg），由服务端签名返回 UploadCredential
   * - signerKind='local' ：用本地 Secret 直接构造（不推荐生产）
   */
  issueUploadCredential(cfg: ImageHostConfig, meta: UploadMeta): Promise<UploadCredential>

  /**
   * 由对象 key 生成可访问 URL。
   * - 公开桶：返回直链（可拼接 cdnHost）
   * - 私有桶：返回短期签名 URL（expiresSec 默认如 600s，渲染时调用）
   */
  urlFor(cfg: ImageHostConfig, key: string, opts?: { expiresSec?: number }): string

  /** 可选：删除对象（编辑器删除图片/清理孤儿时用） */
  delete?(cfg: ImageHostConfig, key: string): Promise<void>

  /** 可选：连接自检（设置页「测试连接」按钮调用），返回是否可达 */
  probe?(cfg: ImageHostConfig): Promise<boolean>
}

3.4 注册表（插件自注册）

const registry = new Map<string, ImageHostAdapter>()

export function registerImageHost(a: ImageHostAdapter): void {
  registry.set(a.id, a)
}
export function getImageHost(provider: string): ImageHostAdapter | undefined {
  return registry.get(provider)
}
export function listImageHosts(): ImageHostAdapter[] {
  return [...registry.values()]
}

4. 上传编排（框架统一实现，非插件职责）

src/services/imagehost/useImageUpload.ts 实现一次，所有适配器复用：

export async function uploadImage(
  cfg: ImageHostConfig,
  file: Blob,
  meta: UploadMeta,
): Promise<{ url: string; key: string; width?: number; height?: number }> {
  const adapter = getImageHost(cfg.provider)
  if (!adapter || !adapter.isConfigComplete(cfg)) throw new Error('图云未配置')
  const cred = await adapter.issueUploadCredential(cfg, meta)
  // 按 cred.method 直传（PUT / POST / POST-FORM），可带进度回调
  const ok = await putToCloud(cred, file)
  if (!ok) throw new Error('图云上传失败')
  const url = adapter.urlFor(cfg, cred.fileKey)   // 私有桶可改为渲染时再签名
  return { url, key: cred.fileKey, width: meta.width, height: meta.height }
}

编辑器调用 uploadImage 拿到 url 后，把 ![](url) 插入 markdown。粘贴图片的现有 paste-image.ts 改为「压缩 → 调 uploadImage → 插入 URL」，不再内联 data URI。

5. 配置页渲染（configSchema 驱动）

SettingsSheet.vue 新增「图云」分组，逻辑完全数据驱动：

  • 「启用图云」开关 → cfg.imageHost.enabled
  • 「图云厂商」下拉 → listImageHosts().map(a => ({ label: a.name, value: a.id }))
  • 选中后，遍历 getImageHost(provider).configSchema 动态渲染字段（switch on field.type）
  • 保存时整段写回 cfg.imageHost，调用 store.saveConfig（仅落本地）
  • 「测试连接」按钮 → 调 adapter.probe?.(cfg.imageHost) 或发一次最小 issueUploadCredential
因为字段来自 configSchema，新增图云无需改设置页模板——这是「AI 开发友好 + 配置化」的核心。

6. 签名服务（Signer）设计

为解决「密钥不下发」（红线 5），推荐 signerKind='remote'：

  • 前端持有 cfg.imageHost.signerUrl（一个你部署的 HTTPS 端点，URL 本身非机密）。
  • 服务端（Cloudflare Worker / 腾讯云函数 / 阿里 FC …）持有 SecretKey，按 adapter 的规则签发 UploadCredential 返回。
  • 项目已有 proxy/cloudflare-worker.js，最顺的落点是扩展该 Worker 增加一个 /img-sign 路由，按 provider 分发到各图云的签名逻辑（七牛 uptoken、COS/OSS/R2 预签名 URL）。
// 请求：POST {signerUrl}  body: { provider, meta: UploadMeta, cfg: 非机密字段 }
// 响应：200 { credential: UploadCredential }
// 失败：4xx/5xx { error }
这样每种图云的「密钥 + 签名算法」天然隔离在各自的服务端分支里；前端适配器即使被读源码也拿不到 Secret。

7. 参考实现骨架

7.1 适配器模板 src/services/imagehost/adapters/_template.ts

import type { ImageHostAdapter, ImageHostConfig, UploadCredential, UploadMeta } from '../types'

export const templateAdapter: ImageHostAdapter = {
  id: 'template',
  name: '模板图云（请复制改名）',
  signerKind: 'remote',                    // 生产用 remote
  configSchema: [
    { name: 'bucket', alias: '存储桶', type: 'input', required: true, message: 'my-bucket' },
    { name: 'region', alias: '地域', type: 'input', required: false },
    { name: 'cdnHost', alias: 'CDN 域名(可选)', type: 'url', required: false },
    { name: 'publicRead', alias: '公开读', type: 'list', required: false,
      choices: [{ name: '是', value: 'true' }, { name: '否', value: 'false' }] },
  ],
  isConfigComplete(cfg) {
    return !!cfg.signerUrl && !!cfg.bucket
  },
  async issueUploadCredential(cfg, meta) {
    const r = await fetch(cfg.signerUrl!, {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ provider: this.id, meta, cfg: stripSecret(cfg) }),
    })
    if (!r.ok) throw new Error('签名失败 ' + r.status)
    return (await r.json()).credential as UploadCredential
  },
  urlFor(cfg, key, opts) {
    const host = (cfg.cdnHost as string) || `https://${cfg.bucket}.example.com`
    return `${host}/${key}`                 // 私有桶改为返回签名 URL
  },
}

// 仅保留非 secret 字段发给签名服务
function stripSecret(cfg: ImageHostConfig): Record<string, unknown> {
  const out: Record<string, unknown> = { ...cfg }
  delete out.signerUrl
  return out
}

7.2 各厂商差异点（AI 实现时只需关注这几处）

厂商signerKindissueUploadCredential 产物urlFor 规则服务端签名要点
七牛 KodoremotePOST-FORM + token(uptoken)cdnHost/key服务端用 SecretKey 算 uptoken（PUT 策略 + deadline）
腾讯云 COSremotePUT 预签名 URLbucket.cos.region.myqcloud.com/key（或 cdnHost）服务端用 SecretId/Key 算 COS 签名 v5
阿里云 OSSremotePUT 预签名 URLbucket.oss-region.aliyuncs.com/key服务端算 OSS Signature
Cloudflare R2remotePUT 预签名 URL（S3 兼容）cdnHost/key服务端用 AccountId/Key 算 S3 V4 签名

通用 CLI（upgit 类）remote调外部 HTTP 服务返回 URL服务返回你自己的中转
AI 友好性结论：无论哪种图云，前端适配器模板几乎一致（都是「POST signerUrl → 拿 cred → 直传 → urlFor」），差异 90% 在服务端签名分支。因此一个新图云的接入工作量 ≈ 写 configSchema + 改 urlFor 拼接 + 在 Worker 加一个签名分支。

8. 新增一个图云的 5 步（AI/开发者 SOP）

  1. 复制 _template.ts → adapters/<provider>.ts，填 id / name / configSchema。
  2. 实现 isConfigComplete 与 urlFor（纯字符串拼接，无网络）。
  3. 实现 issueUploadCredential：默认 POST signerUrl 即可，无需改。
  4. 在签名服务（Worker/云函数）加该 provider 的签名分支，返回对应 UploadCredential。
  5. 文件底部 registerImageHost(xxxAdapter)；设置页自动出现该选项。
第 3 步前端在模板里已通用，多数图云只需改第 2、4 步。
另：ConfigField 字段命名已对齐 PicGo（见 §14），可低成本复用社区上传器逻辑。

9. 与现有同步的衔接（零侵入）

  • 图片外置后，article.content 从「含 data URI 的大文本」变为「含 URL 的小文本」，kb/<id>.md 体积回归 KB 级。
  • 现有同步引擎（src/services/sync/engine.ts）、manifest、contents.ts 完全不用改；且因文章变小，前序讨论的「增量同步」「localStorage 5MB 危机」一并缓解。
  • Config 仅新增 imageHost?: ImageHostConfig 一个字段（src/types/index.ts），存 wb.cfg.v1，不上传（与 token 同待遇）。
  • 设置页 SettingsSheet.vue 仅新增一个数据驱动的「图云」分组，不改既有 GitHub 同步逻辑。

10. 从内联 data URI 迁移（可选，一次性）

对已有含 data:image/... 的历史文章，提供一次性迁移脚本/按钮：

  1. 遍历 articles，正则提取正文中的 data:image/...;base64,XXX。
  2. 逐个 uploadImage 上传，拿到 URL，替换原 data URI。
  3. touch() + 触发一次同步推送。
  4. 迁移幂等：已为 URL 的不处理；失败项记录跳过，不阻塞。
该迁移属「可选项」，不阻塞图云接入；新写入直接走 URL，历史数据可后续清理。

11. 测试策略

  • 接口契约测试：用一个 mockAdapter（本地 signerKind='local'，返回假 cred）验证 useImageUpload 编排、设置页 configSchema 渲染、注册表查找。
  • 适配器单测：对每个真实适配器，mock signerUrl 的 fetch 响应，断言 issueUploadCredential 产物结构、urlFor 拼接正确（覆盖公开/私有、cdnHost 有无）。
  • 签名服务单测：Worker/云函数侧对每种 provider 的签名分支做单测，确保返回的 UploadCredential 能被对应图云接受（可用各厂商 SDK 校验）。
  • 现有 src/services/sync/__tests__/ 体系沿用，新增 src/services/imagehost/__tests__/。

14. 参考实现（Prior Art）

本方案并非凭空设计，以下成熟实现已验证「可插拔图云 + 配置驱动 UI + 服务端签名」的可行性，可直接借鉴其契约：

14.1 PicGo（Uploader 插件契约）—— 主参考

PicGo 的每个图床即一个 Uploader 插件，通过 ctx.helper.uploader.register(id, { handle, config }) 自注册，config(ctx) 返回字段数组由 CLI/GUI 自动渲染成表单。其字段形态与本方案的 ConfigField 几乎同构：

本方案 ConfigFieldPicGo 字段说明
namename字段名，作配置 key
aliasaliasGUI 表单标题
typetype（input/password/list/confirm/editor/checkbox）渲染类型
requiredrequired必填
defaultdefault默认值（对齐新增）
messagemessage占位/提示
choiceschoices（[{name,value}]）下拉项（原 options）
tipstipstooltip（原 help）
secret—（本方案扩展）标记敏感字段，remote 模式不落前端

借鉴点：插件自注册 + config 字段数组 + 按 required 自动校验，已被社区几十种图床（七牛/COS/OSS/R2/GitHub）验证。本方案 §3.1 的 ConfigField 已直接对齐该命名，未来可低成本「翻译」复用社区上传器逻辑。

14.2 S3 预签名 PUT 范式 —— 签名服务端通用分支

Cloudflare R2 / 阿里云 OSS / 腾讯云 COS 均实现同一套 S3 兼容预签名上传。意味着一个 s3-compatible 适配器即可覆盖 R2+OSS+COS 三家，仅需配置 endpoint/region/bucket；签名服务端（Worker）也只需一个通用 S3-V4 签名分支。

14.3 upgit / 自定义 HTTP 后端 —— remote 签名模式来源

upgit 等工具支持「调一个外部 HTTP 接口返回 URL」作为自定义后端。这正对应本方案的 signerKind:'remote' + signerUrl：外部签名服务返回一次性上传凭证/URL 是通用范式，非本方案独创。

14.4 Lsky Pro（兰空图床）—— 自托管图云参考

开源自托管图床，提供固定 REST API。若不想用商业云，直接照其 API 写一个 adapter 即可，对应 signerKind:'remote' 的另一种签名后端形态。

14.5 关键差异（必须保留本方案设计）

PicGo 是桌面应用（Electron），密钥存本地配置，无「服务端签名」概念；本方案是浏览器应用，必须守红线 5——密钥不下发前端。因此：借 PicGo 的插件契约与 config 字段形态，但保留本方案的 signerKind:'remote' + signerUrl 服务端签名层（PicGo 没有、而我们必须有）。
