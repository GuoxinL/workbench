### 发现并修复的真实链路 Bug（已随同部署修复）
- **现象**：首次同步报「同步失败 · GithubError: is at … but expected …」，胶囊变红；但重试即成功。
- **根因**：`repoFile.putFile/deleteFile` 仅把 HTTP **409/422** 转成可重试 `ConflictError`；GitHub（或代理）对版本冲突有时返回**非 409 状态 + "is at X but expected Y" 文案**，被当成硬错误裸抛，绕过冲突重试 → 首次同步直接红点且无法自愈。
- **修复**：在 `repoFile.ts` 增加 `isConflictMessage()`，凡消息含 `does not match|but expected|conflict|out of date` 的 `GithubError` 一律视为可重试冲突（无论 HTTP 状态）；新增单测 `pushRemote 遇非 409 的 sha 冲突文案 → 仍返回 conflictSlug 自愈`。见任务 #10 / 03-implement.md。

### 结论
核心改造（目录树索引替代中央 manifest.json + 每文件 blob sha 判定 + 单文件粒度乐观锁/重试 + 墓碑 DELETE）在**真实数据仓库**上验证可用；首轮偶发冲突已通过硬化转为自愈。IT-1/IT-2 的多设备并发场景建议在用户侧用两个浏览器 profile 复跑以覆盖完整并发矩阵（本会话单 profile 已覆盖 pull/push/delete 单链路）。
