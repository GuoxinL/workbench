# 个人工作台

待办卡片 + 双向链接笔记，状态实时同步到你自己的 GitHub 仓库。纯静态页面，**无需后端、无需构建**。

本应用设计为直接托管在 **GitHub Pages**，电脑和手机浏览器都能访问，手机上「添加到主屏幕」即全屏当 App 用。

## 功能

| 模块 | 说明 |
| --- | --- |
| 待办管理 | 卡片式待办，8 种颜色分类，三档状态（待办 / 进行中 / 已完成），支持截止日期、颜色筛选、状态筛选、关键词搜索 |
| 笔记查阅 | Markdown 实时渲染，阅读 / 编辑双模式，桌面端左右分栏对照 |
| 待办转笔记 | 卡片上一键转换，自动带入标题、描述、颜色、状态、截止日期，双方保留互跳入口 |
| 双向链接 | `[[笔记标题]]` 建立引用；A 引用 B 后，A 显示「引用了」，B 显示「被引用」并附上下文摘录 |
| 关联图谱 | 力导向图展示笔记引用网络，可拖拽、缩放，点击节点直达笔记 |
| GitHub 同步 | 数据落成仓库里的一个 JSON 文件，多端读写同一份，自动合并冲突 |

## 一、部署到 GitHub Pages（让电脑 / 手机都能访问）

GitHub Pages 部署的是**代码静态文件**；真正的工作数据走另一套（见第二、三节）。

### 1. 新建代码仓库

在 GitHub 新建一个**公开**仓库（Pages 对公开仓库免费；页面只是前端外壳，不含任何数据）。

> 勾选 "Add a README file"，避免空仓库没有默认分支。假设仓库名为 `workbench`。

### 2. 推送代码

本目录已经 `git init` 并完成初次提交。你只需关联远程并推送：

```bash
cd workbench
git remote add origin https://github.com/你的用户名/workbench.git
git branch -M main
git push -u origin main
```

> 以后改了代码，`git add -A && git commit -m "更新" && git push` 即可，Pages 会自动更新。

### 3. 开启 Pages

仓库 → **Settings → Pages → Build and deployment → Source** 选 **Deploy from a branch**，
分支选 **main**，目录选 **/ (root)**，保存。

一两分钟后访问 `https://你的用户名.github.io/workbench/` 即可。

### 关于路径

代码全部使用相对路径 + hash 路由，已适配 GitHub Pages 的子路径（`/workbench/`），**无需任何 base 配置**。
根目录的 `.nojekyll` 文件用于关闭 Jekyll，避免文件被误当作模板处理。

## 二、准备数据仓库（存放你的待办与笔记，务必私有）

> 同步用的是 GitHub **Contents API**，与上面部署代码的仓库是独立的两回事。
> Pages 站点必然公开，所以**数据一定要放在另一个私有仓库**里。

新建一个**私有**仓库，例如 `workbench-data`，空仓库即可（首次同步会自动创建数据文件）。

> 新建时勾选 "Add a README file"，避免出现空仓库没有默认分支的情况。

## 三、生成访问令牌

推荐细粒度令牌，权限最小化：

1. GitHub → Settings → Developer settings → **Personal access tokens → Fine-grained tokens** → Generate new token
2. **Repository access** 选 Only select repositories，勾选上面的**数据仓库** `workbench-data`
3. **Permissions → Repository permissions → Contents** 设为 **Read and write**
4. 生成后复制 `github_pat_...`（只显示一次）

> 也可用经典 token（Tokens classic），勾选 `repo` 权限。

## 四、在应用里填入并启用同步

打开 Pages 站点 → 右上角齿轮 → 填写：

- **仓库**：`你的用户名/workbench-data`
- **分支**：`main`
- **数据文件路径**：`data/workbench.json`
- **访问令牌**：粘贴上面的 token
- 打开「启用同步」开关

先点「测试连接」确认通过，再点「保存并同步」。顶栏出现绿点即同步正常。

在另一台设备 / 手机上打开同一个站点，重复第四步填相同的仓库与路径，两端数据即互通。

## 五、同步失败怎么排查

设置面板里点 **「诊断」**，它会分五步逐项检测并指出具体卡在哪一环：

| 诊断步骤 | 失败含义与处理 |
| --- | --- |
| 配置检查 | 仓库格式必须是 `owner/repo`，路径、令牌不能为空 |
| 网络连通 | **打不通 `api.github.com`**——见下方「网络不通」一节 |
| 令牌有效性 | 401 表示 token 写错、被撤销或已过期，重新生成即可 |
| 仓库访问 | 404 多为仓库名写错，或细粒度令牌没在 *Repository access* 里勾选这个仓库 |
| 数据文件 | 远端 JSON 损坏时会提示；文件不存在属正常，首次同步会自动创建 |

常见错误对照：

- **`Token 无效或已过期`** — 重新生成令牌。注意细粒度令牌有有效期，过期需重签。
- **`仓库或分支不存在，或 Token 无该仓库权限`** — 三个都要查：仓库名拼写、分支名（默认 `main`，老仓库可能是 `master`）、令牌授权范围。
- **`Token 对该仓库没有写入权限`** — 令牌权限需要 **Contents: Read and write**，只给 Read 无法同步。
- **`API 调用频率超限`** — 认证后每小时 5000 次，通常是轮询间隔调得过小，改回 20 秒以上。
- **`远端数据文件不是合法 JSON`** — 仓库里那个文件被手工改坏了，删掉它让应用重建，或用「导出备份」的内容覆盖回去。

### 网络不通：使用 API 代理

如果诊断卡在「网络连通」，说明你的浏览器根本连不上 `api.github.com`。此时需要一个中转地址，填进设置里的 **「API 代理地址」**，填入后所有请求改走该地址。

仓库内已附带一份可直接部署的中转脚本：`proxy/cloudflare-worker.js`

1. 登录 Cloudflare → Workers & Pages → Create → Worker
2. 把该文件内容整段粘贴进去，Deploy
3. 得到形如 `https://xxx.workers.dev` 的地址，填进「API 代理地址」
4. 再点「诊断」，网络那一步应显示「经代理」

这个脚本做了三件必要的事：转发 `Authorization` 头、返回 CORS 响应头（否则浏览器会拒绝）、限制只放行工作台用到的接口以防被当成公共代理滥用。默认还限制了来源站点，脚本里的 `ALLOW_ORIGINS` 改成你自己的 Pages 域名即可。

> **令牌安全**：代理会看到你的令牌明文。务必只填自己部署的服务，不要用来路不明的公共代理。若 `workers.dev` 域名在你的网络同样受限，需在 Worker 设置里绑定自有域名。

## 同步机制

- **推送**：任何改动后防抖 1.5 秒自动提交
- **拉取**：默认每 20 秒轮询一次（可在设置里调整 5–300 秒），切回页面、网络恢复时立即同步
- **合并**：逐条记录按 `updatedAt` 时间戳取较新者，不是整文件覆盖，所以两端同时编辑不同条目不会互相丢数据
- **冲突**：提交时带 sha 乐观锁，若远端已变更则自动重新拉取合并后重试（最多 3 次）
- **删除**：软删除保留墓碑记录，确保删除动作能传播到其它设备；30 天后自动清理

同一条记录被两端同时修改时，以最后写入的为准——这是无后端方案的固有取舍。

## 笔记语法速查

```markdown
[[Q3 规划]]              引用另一篇笔记
[[指标口径说明|口径]]     引用并自定义显示文字

# 标题        **粗体**    *斜体*    ~~删除线~~   ==高亮==
- 列表        1. 有序列表
- [x] 已完成任务   - [ ] 未完成任务
> 引用块      `行内代码`   ```代码块```
| 表格 | 支持 |
```

编辑时输入 `[[` 会自动弹出笔记候选，方向键选择、回车插入；输入不存在的标题可直接回车创建新笔记。

**改标题会自动修正其它笔记里的引用**，双链不会断。

## 安全说明

- Token 仅存放在本机浏览器 localStorage，不经过任何第三方服务器，只与 `api.github.com` 通信
- **代码仓库可公开，数据仓库务必私有**——Pages 站点公开，但你的待办 / 笔记内容只在私有仓库里
- 在公共电脑使用后，记得在设置里清空 token
- 每次改动会产生一次 commit，数据历史在仓库里可完整回溯
